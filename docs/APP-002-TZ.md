## 1. Общая задача

Нужно развивать существующий веб-каталог VR-игр, программ, утилит и VR-модов.

Это не просто таблица, а личное мини-приложение для выбора:

- во что играть;
- где лучше играть — Meta Quest или Steam/PCVR;
- что уже пробовал;
- что сейчас пробую;
- что стоит купить;
- что бесплатное;
- насколько игра подходит пользователю;
- насколько велика вероятность укачивания;
- какие программы нужны для Quest / PCVR;
- какие игры лучше брать именно в Steam, даже если они есть и на Meta.

Главный принцип:

> пользователь должен за несколько секунд выставить фильтры и получить только тот список, который ему сейчас нужен.

Пример:

`Игра → Бесплатная → Есть в Meta → Экшен → рейтинг 8–10 → не пробовал`

После этого на экране остаются только подходящие позиции.

# 6. Где лучше играть

Это отдельное поле, не путать с доступностью.

Значения:

- Steam лучше
- Meta лучше
- Равно / по ситуации
- —

Логика пользователя:

Если игра есть и на Meta, и в Steam, но Steam-версия объективно лучше, каталог должен показывать:

**Доступность:** Meta + Steam

**Где лучше:** Steam лучше

Пользователь сначала будет искать Steam-версию.

Meta-версия нужна:

- если Steam-версию не удалось найти;
- если хочется сначала быстро попробовать;
- если standalone-версия удобнее;
- если отсутствие задержки важнее графики.

# 7. Принцип выбора Steam vs Meta

Steam/PCVR ставить выше, если важны:

- графика;
- текстуры;
- освещение;
- моды;
- качество моделей;
- дальность прорисовки;
- возможности RTX 3080;
- крупная сюжетная игра.

Meta ставить выше, если важны:

- минимальная задержка;
- отсутствие зависимости от ПК;
- активные ритм-игры;
- фитнес;
- настольный теннис;
- игры стоя на месте;
- быстрый запуск;
- mixed reality.

Примеры Meta-приоритета:

- Beat Saber
- Pistol Whip
- Synth Riders
- Eleven Table Tennis
- Walkabout Mini Golf

Примеры Steam-приоритета:

- Metro Awakening
- Walking Dead
- Skyrim VR
- Fallout 4 VR
- Into the Radius
- Arizona Sunshine
- крупные PCVR-проекты.

# 9. Рейтинг

Каждая игра должна иметь рейтинг:

`0–10`

Показывать минимум одну цифру после запятой при необходимости.

Пример:

- 9.5
- 8.8
- 7.4

Рейтинг должен отражать не только общую известность игры, но и полезность именно для данного каталога.

Факторы:

- качество игры;
- качество VR-механик;
- отзывы;
- насколько игра актуальна;
- насколько она интересна владельцу Quest 3;
- качество конкретной VR-версии;
- комфорт;
- наличие более сильного продолжения.

# 31. Пользовательские данные, GitHub и Supabase

GitHub хранит общий каталог и канонический исходный код приложения.

Пользовательские данные должны храниться в Supabase MINI-APPS-CLOUD под APP-ID `APP-002`.

В облако синхронизируются:

- пользовательские статусы;
- впечатление;
- решение о покупке;
- комментарии;
- сохранённые виды;
- фильтры;
- выбранные колонки;
- сортировка.

`localStorage` сохраняется как быстрый локальный кэш и аварийный временный слой, но не считается единственным источником пользовательских данных.

После очистки браузера пользователь должен иметь возможность войти в тот же Supabase-профиль и получить свои данные обратно.

Статический справочник игр/программ (`data-*.js`) остаётся в GitHub и не обязан дублироваться в Supabase.

# 32. Облачная синхронизация между устройствами

Облачный этап утверждён и входит в текущую версию APP-002.

Архитектура:

`GitHub Pages → Supabase Auth → mini_app_state(APP-002)`

Используется тот же профиль MINI-APPS-CLOUD, что и у других мини-приложений.

Первый вход после миграции должен:

1. загрузить облачное состояние APP-002;
2. если это первая миграция — объединить существующие локальные пользовательские изменения с облаком;
3. сохранить результат в Supabase;
4. далее использовать облако как постоянный пользовательский слой.

Интерфейс не должен ждать сеть при обычной сортировке, фильтрации и редактировании. Изменения сначала применяются локально мгновенно, затем отправляются в Supabase асинхронно с задержкой/debounce.

При открытии того же приложения на телефоне под тем же аккаунтом должны быть доступны те же пользовательские статусы, комментарии и сохранённые виды.

Не делать интерфейс «красивым ради красивого».

Приоритет:

1. быстро найти нужные позиции;
2. быстро убрать лишние колонки;
3. быстро понять игру;
4. быстро понять Meta или Steam;
5. рейтинг;
6. бесплатность;
7. комфорт;
8. статус пользователя.

# 38. Требование к мобильной версии

Сайт должен нормально открываться на телефоне.

Не обязательно показывать 20 колонок.

На узком экране:

- фильтры должны складываться;
- таблица может скроллиться;
- выбор колонок должен работать;
- карточный режим позже может стать основным для мобильного.

## Критерии приёмки облачной миграции

- вход тем же email/паролем, что и в MINI-APPS-CLOUD;
- существующие локальные статусы/комментарии не теряются при первом входе;
- изменение статуса или комментария сохраняется после F5;
- те же данные появляются на телефоне после входа в тот же аккаунт;
- очистка localStorage не уничтожает облачные пользовательские данные;
- фильтрация/сортировка остаются мгновенными и не ждут ответа Supabase;
- GitHub Pages URL остаётся постоянным;
- при отказе Supabase интерфейс не должен молча уничтожать локальные данные.
